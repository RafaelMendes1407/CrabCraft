# Reviewed SFTP and explicit-FTPS deployment

Open **Remote files → Reviewed file deployment** in a trusted local workspace. Select a regular disk file, protocol, destination path and whether to create a new file or replace an existing one. Preview reads and freezes the local file and remote state on a cancellable worker. It displays the protocol/host/port, source/destination, byte sizes, SHA-256 hashes and a bounded text excerpt when available. Preview does not upload file data. Check the review acknowledgement and choose **Confirm deployment** to transfer that snapshot. Unsaved editor buffers are not included; save them before previewing if their edits should be deployed.

Opening a project or tool window starts no network operation, authentication or remote command. Both preview and confirmation require project trust. Deployment never builds or executes the selected file, automatically uploads on save, recursively synchronizes a directory or installs a remote agent. Connections, credentials, previews and receipts are session memory only. Confirmation rechecks the current connection settings and local bytes/metadata, and re-reads the remote destination before publishing. A stale source/destination fails instead of silently replacing its new version. The resulting file is verified against the frozen source SHA-256/size; success includes the actual final path.

## SFTP

The SFTP deployment client is a bounded Rust SFTP-v3 packet implementation over the existing verified OpenSSH `ssh -s … sftp` subsystem. It uses the SSH host/key/known_hosts fields above the deployment section, private temporary key/host snapshots, `-F none`, strict host-key checking and the existing batch/agent/proxy/forwarding restrictions. No shell interprets paths or file bytes. It supports regular remote files only; LSTAT refuses symlinks and nonregular destinations. A missing file is accepted only from the protocol's explicit `SSH_FX_NO_SUCH_FILE` status, not from an error-message guess.

The client uploads to an adjacent temporary file opened with CREATE|EXCL, writes binary chunks, uses the OpenSSH fsync extension when available, and verifies its contents before publishing. New destinations use **standard SFTP-v3 RENAME**, whose protocol contract refuses an already existing destination. The tested OpenSSH server preserves a file created by a concurrent writer even if it appears after the final absence check. Replacing an existing destination requires `posix-rename@openssh.com`; servers without it fail without a remove-before-rename fallback. Ordinary existing permission bits are retained on replacement; a new file requests ordinary local permission bits. Ownership, ACLs, extended attributes, hard links and special bits are not preserved.

File identity includes content hashes, sizes and reported modification/permission/owner metadata. Access time is deliberately excluded: reading a file may update it. Neither SFTP nor the POSIX rename extension provides atomic content compare-and-swap. An existing destination can change after the final check and before replacement. This is not a lock against concurrent writers. Errors/cancellation can leave the owned temporary file; a completed rename can already have committed.

## FTP support is explicit FTPS

The supported FTP workflow is **explicit FTPS**: a native Rust client upgrades the control connection with AUTH TLS, verifies the certificate chain/hostname and optional SPKI pin, then authenticates and requires PBSZ 0 / PROT P. Data connections also require verified TLS. TLS 1.2 and TLS 1.3 are supported. There is currently no plaintext FTP or implicit-FTPS mode, fallback or insecure-verification option. This describes the supported protocols, rather than all FTP servers.

Enter FTPS host/IPv4, port, user, password, optional CA bundle and optional `sha256//…` SPKI pin. With no CA bundle, the native/system certificate store is loaded. A provided CA bundle supplies explicit trust roots. Pins are checked in addition to PKI/hostname validation on both control and data TLS; a matching pin does not accept an untrusted certificate. CA inputs must be bounded regular local non-symlink files. The client uses rustls/tokio-rustls, not an external curl process: credentials appear in no process argv, command/config file, console output or persisted session. Its Debug representation redacts them. The server may maintain its own authentication logs; the IDE does not control that server policy.

The client requires EPSV, MLSD and UTF-8 responses/names. A data socket connects only to the control connection's peer IP and an EPSV port; no server-selected PASV IP is followed. All transfers use TYPE I so source bytes, including binary data and CRLF, remain unchanged. The client flushes upload TLS, exchanges close_notify/EOF before dropping the data socket, requires a completion reply and verifies the resulting content. Immediate TCP close is insufficient: a real Rust-binary test exposed truncation, and graceful TLS shutdown fixed it without relaxing hash verification.

Destination paths are absolute in the server's **FTP virtual filesystem**, not necessarily host filesystem paths. Its parent directory must already exist. MLSD gives a complete bounded directory listing; permission/unsupported-listing errors do not become a claim that the destination is missing. Case aliases that cannot be distinguished safely are refused.

New files use real **STOU**: the server creates a unique name without overwriting an existing file. The preview explicitly states that the final name is server-generated, and the receipt shows it. The server must return the RFC-1123 `FILE: …` pathname in its preliminary reply. This supports new file creation without pretending an exact-name, no-clobber publish is available through FTP rename. A file created concurrently at the requested name remains intact. The unique final file can be visible during upload; cancellation can leave it partial.

Replacement uploads with STOU to a unique adjacent temporary file, verifies it, rechecks the original destination and publishes through RNFR/RNTO. It never deletes the destination before rename. FTP rename offers no standard content compare-and-swap, so the same final-check race applies to replacements. Server-side default permissions/ownership and rename semantics apply; the client does not issue SITE CHMOD or delete a destination. Interrupted/failed replacement may leave its unique temporary file. Inspect the server before retrying an uncertain result.

## Limits and evidence

Files are limited to 32 MiB each. Local descriptors are checked for regular-file status, no-follow/nonblocking on Unix, stable path/descriptor metadata and bounded chunked reads with cancellation. Before/after text excerpts are at most 8192 characters and only for UTF-8 files up to 64 KiB; binary/large files are reviewed by hashes and sizes. Remote/source snapshots use bounded memory and are not saved as deployment profiles.

SFTP packets are at most 128 KiB, opaque handles/paths are bounded, stderr is capped/discarded, chunks are 32 KiB and a connection has a 120-second deadline. FTPS lines are at most 8 KiB, multiline control responses 64 KiB, MLSD data 2 MiB/4096 entries, leaf certificates 128 KiB and configured CA bundles 256 KiB/64 certificates. Connect has a five-second bound and each FTPS connection a 120-second deadline. Cancel interrupts protocol/TLS I/O and cancels the OpenSSH process tree where used. Disk/network limits are application budgets, not an operating-system filesystem quota or isolation boundary.

Real evidence uses the private loopback OpenSSH server and an explicit-FTPS pyftpdlib server with a separate CA and CA:FALSE serverAuth leaf certificate. It covers:

- An actual compiled Rust executable deployed by SFTP, byte/hash verification and explicit execution by the test; new and replacement paths, stale local/remote rejection, host-key refusal, and a concurrent new destination preserved by standard rename.
- Rust source and a compiled binary through real FTPS, exact byte/hash verification, STOU new names, RNFR/RNTO replacement, stale remote rejection, wrong CA/pin/authentication, TLS control/data and graceful upload completion.
- A concurrent existing FTPS target preserved by STOU, and prompt cancellation during an actual throttled TLS upload; cancellation of an active stalled SSH handshake.
- Native whole-app controls for both protocols: untrusted preview does nothing, preview transfers no artifact, confirm is disabled before review acknowledgement, real pointer/scroll interaction confirms, returned hashes match artifacts, build.rs never executes and serialized sessions contain no FTPS password.
- Pure packet/DER/reply parsers, credential Debug redaction, special-file/symlink refusal and no-network native trust gates.

These are real protocol sessions on the same machine/UID, not WAN or physically separate-host evidence, and do not claim compatibility with every SFTP/FTP server or RustRover parity. Native tests use the actual asynchronous workspace loader before configuring the Remote dock. Opt-in transport tests require the privately prepared services and configuration under `/tmp/crabcraft-ssh` and `/tmp/crabcraft-ftps`; none starts a server, installs dependencies or runs automatically in the ordinary suite.
