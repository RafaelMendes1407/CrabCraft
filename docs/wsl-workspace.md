# WSL Rust workspace — awaiting real Windows validation

P-04 remains **in progress**. The adapter and native workflow are implemented, but the development host is Linux and has no real Windows/WSL installation. A Linux executable fixture exercises argument boundaries, the Linux file bridge, the shared language server and Cargo. Those tests are not proof that `wsl.exe` works on Windows. The UI states this limitation. On Linux and macOS, Start and distribution enumeration are disabled and no WSL process runs.

On Windows, choose **Code → WSL Rust workspace…** or Find Action. The panel reuses the native workspace editor, separate Linux document namespace, background parsing, reviewed writes, diagnostics, completion, definition navigation, hover, cancel and disconnect from [remote development](remote-development.md). It does not open a webview or reinterpret local/UNC paths as Linux files.

Configure an existing distribution, Linux user, absolute Linux workspace root and absolute Linux Cargo and rust-analyzer executables. Listing installed distributions is a separate explicit operation (`wsl.exe --list --quiet`); neither project opening nor panel opening enumerates or starts a distribution. UTF-8 and UTF-16LE listing output is bounded and validated. Distribution selection does not automatically trust it. Changing fields revokes the trust box before Start can run. Check the distribution/workspace trust box and explicitly choose **Start WSL workspace**. Start may run Cargo metadata, build scripts and procedural macros inside that distribution.

The launcher is `%SystemRoot%\System32\wsl.exe`. Distribution, user and Linux arguments are separate process arguments: `--distribution <name> --user <user> --exec <program> ...`. The product uses no PowerShell or `cmd.exe`. Linux scripts are fixed templates whose path inputs use the existing validated shell quoting; source text is never interpolated into a shell command. `WSLENV` forwarding is cleared. Bash runs without profiles/rc files or `BASH_ENV`/`ENV` startup hooks. Windows helpers run without a console window. Real Windows command-line behavior, path quoting and process EOF propagation still need Windows/WSL validation.

Cargo, rustc and rust-analyzer run in the selected distribution/user/root, never through a fallback Windows Cargo. Start probes Cargo, the sibling `rustc`, rust-analyzer and isolated Python 3 before initializing the language server. The selected Cargo directory leads the Linux PATH, and `RUSTC`/`RUSTDOC` point to its Linux sibling executables. Keep all three toolchain executables in the same toolchain directory; a missing tool is an error. rust-analyzer's Cargo check-on-save is disabled, while trusted metadata/build-script/proc-macro indexing remains enabled. Explicit Cargo check/build/test refuse dirty workspace buffers until reviewed writes are complete.

File operations use a small fixed Python 3 bridge in that distribution (`/usr/bin/python3 -I -c …`). Requests and UTF-8 text travel through bounded JSON stdin, not command-line arguments or Windows staging files. Isolated Python prevents a local/project `json.py`, user site or PYTHONPATH from hijacking bridge imports. The bridge checks root confinement, regular descriptors, symlinks, file size, metadata and UTF-8; it opens files nonblocking/no-follow to reject FIFOs without waiting. Reads retain BOM and CRLF bytes. Writes require a preview and explicit confirmation, recheck the saved remote baseline, preserve ordinary file permissions, fsync a temporary sibling and replace the destination. Concurrent writers can still race the last check; this is not a file lock or atomic content compare-and-swap. Cancellation may occur after a write has completed.

LSP documents use server-side Unix `file:///…` URIs and buffer/version tickets. No `C:\…`, `\\wsl$\…` or `\\wsl.localhost\…` alias is converted into a local editor document. A user can explicitly select a Linux `/mnt/c/…` path, but it stays a Linux path in the selected distribution. Switching from SSH to WSL or between connection settings refuses to discard dirty buffers. A local workspace switch/close disconnects analysis but retains independent dirty workspace buffers. Reconnect resends them only to matching connection settings. Supported completion is a checked plain edit; snippets/import edits and broad refactorings remain unsupported as in the SSH mode.

The shared Cargo and analyzer watchdogs isolate Linux process groups and kill them when transport stdin closes. Cargo also has a host-side Linux timeout. A separate watchdog group prevents an orphan `cat` from holding process pipes open after completion. Cancellation of the Windows `wsl.exe` tree is implemented; whether each supported WSL version propagates EOF and terminates the Linux group is a required real-host check, not an established result here. Deliberately detached project daemons are outside the guarantee.

Requirements are an already installed WSL distribution with Bash, the Linux utilities `find`, `setsid`, `timeout`, `mkfifo` and `mktemp`, Python 3, Cargo/rustc/rustdoc and rust-analyzer. The IDE does not install, update, import, unregister or terminate a distribution or WSL service. There is no automatic distro choice or tool download. Limits and unsupported editing/refactoring operations are the same as the shared workspace mode; bridge requests are at most 1 MiB, reads 512 KiB and reviewed writable files 64 KiB. Enumeration/file operations have a 15-second deadline and bounded stdout/stderr.

Evidence on Linux: a fixture executable records exact argv and delegates Linux commands directly. Tests prove explicit enumeration, strict UTF-16 decoding, literal distribution names/paths, JSON source isolation, BOM/CRLF, stale refusal, symlink/FIFO rejection, cancellation, the shared real rust-analyzer/Cargo flow and no orphan watchdog on normal exit. The native unavailable-platform test proves opening/list/start run nothing, local dirty buffers remain untouched and switching modes preserves dirty Linux buffers. Existing real OpenSSH tests guard the reused implementation. None of these exercises the Windows WSL runtime.

Before promoting P-04 to ready, use a real Windows desktop and preinstalled WSL distribution with a dedicated Rust fixture. Verify explicit listing/trust/Start; Cargo/rustc/rustdoc/RA versions and distribution/user identity; source editing and reviewed stale writes; completion/definition and compiler diagnostic navigation with Unicode/BOM/CRLF; separation from dirty Windows buffers; reconnect/reload; and cancellation/disconnect of long Cargo and analyzer build scripts using Linux PID checks. Include Windows argument/space/quote handling and an unavailable/missing distribution case. Do not use an arbitrary user project for destructive fixture setup.

References: [Microsoft WSL command reference](https://learn.microsoft.com/windows/wsl/reference), [WSL command documentation source](https://github.com/MicrosoftDocs/WSL/blob/main/WSL/basic-commands.md), and [rust-analyzer configuration](https://rust-analyzer.github.io/book/configuration.html). The bridge is repository source, not a bundled interpreter or third-party asset. No new dependency, binary, model or licensed asset is distributed.
